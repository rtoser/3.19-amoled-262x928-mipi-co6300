# 示例按平台自包含，不跨平台共享驱动代码

仓库为同一料号提供多个平台的点亮示例（现有 ESP32-P4，计划中的树莓派 / Linux DRM）。每个平台示例在 `versions/<料号>/examples/<平台>-…/` 下**自包含**：面板初始化序列、DPI/DSI 时序、上电与复位延时、触摸芯片协议各自抄进自己的驱动，用该平台驱动模型的原生写法（ESP-IDF 的 `esp_lcd` 组件、Linux 的 `drm_panel` + `input_dev`）。示例之间不 `#include`、不共用构建目标。`versions/<料号>/docs/` 下的厂商初始化文本与数据手册（含 `docs/markdown/` 转换版）是这些事实的唯一 source of truth；每个示例的 README 必须注明其数值对应手册的哪一节。

## 为什么

- 需要共享的只有约 40 行纯数据（15 条 DCS、8 个时序值、5 个延时），且由硬件钉死、自首次提交未变；为它建一个 ESP-IDF 组件和 Kbuild 都能引用的公共头，成本（构建耦合、两套包含路径）大于收益。
- Linux 侧的 module 形状由 DRM / input 驱动模型规定，惯例是每个 panel 驱动自带初始化表，不引用树外头文件；共享头会妨碍 DKMS 打包和将来进内核树。
- 许可不兼容：内核模块必须 GPL-2.0，现有 ESP 代码为 Apache-2.0（Espressif）与 CC-BY-4.0（OSPTEK）；共享头需要另行双许可，得不偿失。

## 否决的方案

在 `versions/<料号>/panel/` 建平台无关的面板描述头（时序 / init 表 / 延时）和 CST3530 解码纯函数，由两个平台 adapter 共同引用（2026-08-29 架构走查候选 1、3、5）。理由见上；将来若平台数量增长到重复维护成本明显（例如 ≥3 个平台且厂商 init 频繁更新），可重新评估。

## 后果

- 同一组面板事实会在每个示例里各出现一次；厂商更新初始化序列时，先改 `docs/`，再逐个示例跟进，并在示例 README 里记录与 `docs/` 的差异（如 ESP 示例的 `2A` 列窗口与厂商文本不同）。
- 单个示例内部仍应做到每个事实只写一次（见 ESP 示例整理 spec）；本决定只禁止**跨示例**共享，不放松示例内部的单一来源要求。
- 各示例可独立选择许可：ESP 示例沿用现状，Linux 示例内核模块用 GPL-2.0-only。
